## עובדות מסוננות שניתן לקבע ללא mutation

- Production origin/Site URL הקנוני: `https://predictor-swart.vercel.app`.
- Production callback הקנוני:
  `https://predictor-swart.vercel.app/auth/confirm`.
- Local origin הקנוני: `http://localhost:3000`; callback:
  `http://localhost:3000/auth/confirm`.
- loopback חלופי, רק כאשר הוא origin ההרצה שנבחר במפורש:
  `http://127.0.0.1:3000/auth/confirm`.
- Preview Auth הוא QA פנימי אופציונלי ולא דרישת קורס. ה־Preview של PR #14
  נבדק כ־public smoke בלבד; אין כאן claim שה־callback שלו allowlisted.
- בקריאה החיה נצפו Site URL של Production, ‏local callback ו־Production
  callback מדויקים. נצפו גם שני entries היסטוריים של Preview: callback מדויק
  של Slice 1 ו־wildcard ישן של Slice 3. לכן תנאי "אין stale Preview alias"
  עדיין נכשל; לא הוסר דבר כי checkpoint זה read-only.
- **Authentication → Sign In / Providers** הציג `Email Enabled`.
  **Authentication → Emails** הציג default templates ו־`Set up SMTP`, כלומר
  אין custom SMTP והפרויקט משתמש בשירות המובנה.
- **Authentication → Rate Limits** הציג את email control כלא־ניתן לעריכה וללא
  מספר visible. לא הומצא ערך מן המסך. מסמכי Supabase הרשמיים העדכניים קובעים
  לשירות המובנה מכסה project-wide של שתי הודעות לשעה, best-effort, ורק
  לכתובות שהן members בארגון:
  <https://supabase.com/docs/guides/auth/rate-limits> ו־
  <https://supabase.com/docs/guides/auth/auth-smtp>.
- הקריטריון מאפשר custom SMTP **או מנגנון delivery מאושר אחר**. לכן השירות
  המובנה מספיק להדגמת Demo יחידה אם delivery נצפה בפועל; אין הצדקה לרכישה.
- metadata מסונן של Vercel מציג את שמות משתני ה־Production/Preview הצפויים אך
  אינו מספק credential ל־SMTP או disposable recipient. ערכי variables לא
  נקראו ולא נשמרו.

הקריאה מוכיחה configuration בלבד. היא אינה מוכיחה inbox delivery, callback,
password transition או final-SHA parity.

## חלוקת הפעולה שנותרה

**קלט owner עכשיו:** למסור מחוץ ל־Git כתובת מדויקת שנמצאת כבר ב־Supabase
organization ובחשבון Auth מוכר. לפני השליחה נדרש אישור נקודתי לשליחת recovery
אחד; לאחריה ה־owner מחזיר את הקישור מן inbox. אין צורך ב־SMTP credential.

**פעולת agent לפני merge:** לשלוח recovery יחיד דרך Production UI, לעצור,
לקבל את הקישור בלי להדפיסו, ולהוביל callback → password update (עם handoff
ללחיצה הסופית) → replay denied → logout → old/new login. התוצאה מוכיחה רק
שהמנגנון עובד ואינה סוגרת את הרשומה.

**פעולת agent לאחר merge:** להסיר דרך URL Configuration רק את שני entries
ההיסטוריים, בלי לקרוא secret, ולצלם מחדש את כל הראיה על final SHA. באותו
browser/session להריץ בחשבון disposable:
   signup/confirmation לפי הצורך → בקשת recovery לכתובת מוכרת ולכתובת שאינה
   מוכרת עם copy שקול → delivery → callback → session → password update →
   replay denied → logout → old password denied → new password login.
1. ליצור cooldown מורשה בלי לפגוע בנמענים אחרים ולאמת ש־429 מוצג כ־alert
   actionable. לא לשנות rate limit כדי לגרום לבדיקה לעבור ולא לשמור raw header.
2. לתעד רק final SHA, origin/path ללא query, UTC timestamps, שם מנגנון delivery,
   scopes בטוחים, קודי תוצאה allowlisted ותוצאות PASS/FAIL. אין לתעד Email,
   סיסמה, token, cookie, confirmation URL מלא, provider response או screenshot
   שמכיל מידע כזה.
3. להריץ שוב `npm run test:e2e` מקומית ולצרף ראיה נפרדת tied ל־final SHA.

עד שכל ששת הצעדים בוצעו ונצפו, `S9-DEF-004` נשאר
`OWNER_ACTION_REQUIRED`; הוא אינו `VERIFIED`, אינו waiver ואינו ראיית release.
