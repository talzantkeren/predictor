# ראיית מסירה — S9-DEF-011

## תוצאה

`VERIFIED` — client של API-Football מסווג 429 ארוך לפני wait-budget, מחזיר
`PROVIDER_RATE_LIMITED` ללא שינה או retry נוסף, וחוסם את ה־hint ל־`0..3600`.
רק `quota remaining` שלם ולא־שלילי מועבר עם ה־hint ל־orchestrator/finalizer;
headers גולמיים אינם נשמרים. `Retry-After` קצר עדיין יכול לבצע retry ולהצליח.
ה־DB שומר quota ו־backoff מדויק, ודוחה scheduled ו־force בזמן backoff.

לא בוצעה קריאה לספק חי. כל ה־HTTP בבדיקות הגיע מ־transport מוקלט/מזויף.

## Regression חדש

- `API-Football client contract > returns rate-limited immediately for 45 seconds on the default retry path`
- `API-Football client contract > returns rate-limited immediately for 120 seconds on the default retry path`
- `API-Football client contract > returns rate-limited immediately for an HTTP date on the default retry path`
- `API-Football client contract > bounds durable throttle metadata and drops invalid quota or raw headers`
- `shared sports sync orchestration > finalizes a long provider throttle with durable bounded metadata`
- pgTAP: `finalize rejects a retry hint above the durable 3600-second contract`
- pgTAP: `finalize rejects negative provider quota metadata`
- pgTAP: `a finalized 429 failure stores safe quota and the exact bounded provider backoff`
- pgTAP: `a scheduled tick respects provider backoff without creating work`
- pgTAP: `an operator force cannot bypass provider backoff`

הבדיקות של 45/120/date משתמשות ב־`maxAttempts` ברירת המחדל. לפני התיקון המסלול
היה חותך את ה־hint ל־30 ומסיים ב־`PROVIDER_TIMEOUT` מתוך wait-budget, ולכן
הרגרסיות החדשות אינן יכולות לעבור ללא שינוי הסיווג.

## החלטת metadata

הוחלט לשמור ב־`sync_runs.quota_remaining` את `x-ratelimit-requests-remaining`
רק כאשר הוא integer לא־שלילי. שאר quota headers אינם דרושים ל־finalizer,
אינם נשמרים בכשל, ושום header גולמי אינו יוצא מאובייקט ה־client error. החלטה זו
מספקת איתות תפעולי מצומצם בלי לשמר payload או metadata לא־מהימן.

לא השתנתה סכימת DB או חתימת RPC, ולכן לא נדרש generation של טיפוסי Supabase.
