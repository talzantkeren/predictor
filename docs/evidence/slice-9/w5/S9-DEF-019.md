# S9-DEF-019 — ראיית סגירה

## תוצאה

`VERIFIED` מקומית ב־27 באוגוסט 2026. גבולות provider, planner, apply ו־finalize
מחזירים קודים typed, יציבים ובטוחים נפרדים. אין raw exception, ‏SQL, stack,
payload, key או שם קבוצה לא־מהימן בתוצאה או ב־finalizer input. אין migration:
חוזה `error_code` הקיים כבר תומך בקודים בטוחים שרירותיים, ולא השתנו schema,
RPC או חתימת DB.

החלטת counters:

- כשל provider שומר `fixtures_seen=0`, ורק `Retry-After`/quota שכבר נורמלו
  ונחסמו ב־client יכולים לעבור ל־finalize.
- כשל planner שומר `fixtures_seen=0`; snapshot שלא עבר consistency/bounds אינו
  הופך לנתון תפעולי מהימן. quota מנורמלת מותרת.
- כשל apply שומר את `fixtures_seen`, ה־quota וה־operator notes מתוך תכנית
  שכבר עברה validation וחסימה; counters של mutation נשארים בבעלות ה־RPC.
- כשל finalizer אינו מפעיל finalizer פעם שנייה. ה־run/lease נשארים תחת fencing
  וייסגרו במסלול expiry/reclaim הקיים.

## רגרסיות חדשות

`src/features/sync/orchestrator.test.ts`:

- `records a sanitized provider failure and never applies invalid data`
- `classifies a normalized snapshot planner failure without leaking team metadata`
- `retains safe review notes when a later apply batch fails`
- `returns a typed failure when failure finalization also fails`
- `does not re-finalize when the success finalizer fails`

ללא התיקון, provider failure אינו מעביר `fixturesSeen`; planner error מסווג
`PROVIDER_UNAVAILABLE`; ‏`Error` כללי מ־apply מסווג ככשל provider; וכשל
success-finalizer מפעיל finalizer שני ומסווג `SYNC_APPLY_FAILED`.

`src/features/sports/sync-planner.test.ts` מקבע גם שכל הפרות חוזה planner
זורקות `SyncPlannerError` בטוח במקום טקסט פנימי המתאר את הנתון הבעייתי.
