# S9-DEF-022 — מטריצת נגישות ושארית native zoom

Status: `VERIFIED`

סגירת הבעלים: `OWNER_REPORTED PASS` על candidate SHA
`4b77e2412336ed1151849c5db8d05d5947a46e45`. בעל הפרויקט אישר במפורש שב־Chrome
רגיל נבחר **Menu → Zoom → 200%**, ולא CSS zoom, ‏Device Toolbar או emulation.
הוא עבר keyboard-only על `/admin/matches`, על
`/leagues/<owned-league>/members` כולל מצב ה־invalid rejection המתועד, ועל
`/leagues/<owned-league>/settings`; בכל שלושת המסכים ה־focus נשאר גלוי ולא
נצפו חיתוך, חפיפה או horizontal page scroll.

זהו אישור בעלים מפורש ולא תצפית agent. שילוב הדפדפן של ה־agent לא היה זמין,
לא נמסרה שעה מדויקת, ולא נשמרו screenshot או artifact; לכן הרשומה אינה מייחסת
לעצמה אחד מאלה. על בסיס אישור הבעלים, ה־native Chrome page-zoom spot-check עבר
והסעיף מסומן `VERIFIED`.

נצפה ב־28 באוגוסט 2026 על הענף `feature/slice-9-implementation`. תיקוני המוצר
והמטריצה נדחפו ב־SHA
`2decde7e9244a6a0a55baf81b809cdb66858b370`. ‏PR #14 נשאר Draft ולא מוזג;
לא נוצרה, קודמה או שונתה פריסת Production.

כל מטריצת האוטומציה נסגרה גם תחת תהליך Chromium שנפתח עם
`--force-device-scale-factor=2`, ללא override של viewport או DPR. דגל device
scale ו־Chrome **Zoom = 200%** הם מנגנונים שונים, ולכן נדרש בנוסף spot-check
קצר של שלושה מסכים עם פקד Zoom עצמו. ה־spot-check הושלם כעת ואושר מפורשות בידי
בעל הפרויקט כ־`OWNER_REPORTED PASS`, כמפורט לעיל; אין צורך במטריצה ידנית מלאה.

## ההיקף האוטומטי

`e2e/accessibility-matrix.spec.ts` רץ בשני פרופילי Chromium נבדלים — Desktop
Chrome ו־Pixel 5 — בכל אחד מהרוחבים 360/390/768/1024/1440. בכל רוחב נבדקו:

- ארבעת משטחי הכניסה הציבוריים `/`, ‏`/login`, ‏`/register` ו־
  `/forgot-password`;
- ארבעה משטחים מורשים עם fixture מקומי בלבד: `/admin/matches`, ‏`/admin/sync`,
  ‏`/leagues/<owned-league>/members` ו־`/leagues/<owned-league>/settings`;
- מצב שגיאת שרת אמיתי ב־members בכל רוחב: קלט שעובר validation של הדפדפן אך
  מכיל U+202E, החזרת focus ל־textarea, ‏`aria-invalid`, שני מזהי
  help+error ב־`aria-describedby`, ‏alert יחיד והישארות הבקשה במצב ממתין.

בכל route/width המטריצה מאמתת:

- axe WCAG 2 A/AA, ‏2.1 A/AA ו־2.2 AA ללא violation;
- contrast מכריע: findings של axe שניתן לחשב נבדקים כרגיל; glyph דקורטיבי
  שמסומן `aria-hidden` אינו טקסט ישים; ובמקרה שבו pseudo-element או control
  גורמים ל־axe לדווח `partially obscured`, המבחן מחשב מן ה־CSS את יחס
  foreground/background ודורש 4.5:1 לטקסט רגיל או 3:1 לטקסט גדול. finding
  אחר שנשאר בלתי־מוכרע מכשיל את הריצה;
- שם נגיש לא־ריק לכל תחנת focus מתוך accessibility snapshot;
- מעבר Tab בפועל בסדר DOM מדויק, focus בתוך viewport ו־`:focus-visible` עם
  outline או box-shadow גלוי. תחנות UA פנימיות של `datetime-local` נספרות
  כחזרות על אותו element ואינן מורשות לדלג על element או להפוך סדר;
- יעד 44×44 CSS px לכל control וקישור. ב־checkbox/radio נמדד גם ה־label
  המקושר, שהוא חלק מיעד הלחיצה התקני; אין פטור גורף לקישורי טקסט;
- `lang=he`, ‏`dir=rtl`, ללא overflow אופקי, reduced motion וללא שגיאת
  console/page.

בדיקת Vitest נפרדת מאמתת שב־loading של שני מסכי המנהל יש region יחיד בעל שם
ו־`aria-busy=true`, ללא live/status כפול ועם כיבוד reduced motion.

## קירוב 200% — מה נעשה ומה אינו מוכיח

נוצר context חדש ונפרד בכל אחד משני הפרופילים, תוך שמירת מאפייני
user-agent/`isMobile`/touch של אותו פרופיל, עם:

```text
CSS viewport: 720x450
screen: 720x450
deviceScaleFactor: 2
physical screenshot raster approximation: 1440x900
reducedMotion: reduce
routes: 4 public + 4 authenticated + authenticated rejection error state
```

אחרי טעינת viewport metadata נצפו בדיוק `innerWidth=720`,
‏`innerHeight=450`, ‏`devicePixelRatio=2`, וכל חוזי
axe/name/order/focus/contrast/target/RTL/overflow הורצו שוב. ה־context המורשה
קיבל רק את ה־storage state של משתמש fixture מקומי; הוא לא פנה ל־Hosted או
לספק חי.

זהו קירוב reflow ו־pixel density בלבד. הוא אינו משנה את Zoom של Chrome, אינו
בודק את UI הדפדפן ואינו שווה ל־native 200%. בדיקת in-app Browser נפרדת אישרה
בקריאה בלבד שבכל חמשת הרוחבים `clientWidth=scrollWidth` ו־RTL בדף Login, אך
המשטח אינו חושף native zoom. לכן אף אחת מן התצפיות האלה אינה מסומנת כהצלחת
native 200%.

## Chromium forced device scale — תצפית חדשה

נוסף מצב ייעודי שניתן לשחזור בפקודה:

```powershell
npm.cmd run test:a11y:native-scale
```

המצב יוצר חמישה פרויקטי Chromium נפרדים, ברוחבי CSS
360/390/768/1024/1440. בכל פרויקט `viewport: null`; רוחב החלון נקבע באמצעות
`--window-size`, ותהליך הדפדפן נפתח עם
`--force-device-scale-factor=2`. המבחן קורא את שורת הפקודה דרך
`Browser.getBrowserCommandLine` ונכשל אם הדגל חסר. הוא גם דורש:

- `devicePixelRatio=2`;
- `visualViewport.scale=1`, כלומר לא הופעל pinch/page-scale;
- raster בגודל כפול בדיוק מן ה־CSS viewport: ‏720×1600, ‏780×1688,
  ‏1536×2048, ‏2048×1536 ו־2880×1800;
- `viewportEmulation=false` בחמשת קובצי המדידה המקומיים;
- אותם ארבעה routes ציבוריים, ארבעה routes מורשים ומצב rejection אמיתי בכל
  רוחב;
- axe, contrast, accessible names, סדר Tab, focus נראה ובתוך ה־viewport,
  יעדי 44×44 CSS px, RTL, ללא page overflow אופקי, ללא target שאינו בתוך
  viewport או scroller מכוון, וללא חפיפת targets גלויים.

הריצה הנצפית על ה־worktree שמבוסס על head
`138e46f9052234f18ee1660fcf32811e24c5a5ea` הסתיימה כך:

```text
production build: PASS
client-secret scan: PASS across 53 build artifacts
Running 10 tests using 1 worker
10 passed (1.4m)
skipped/disabled: 0
Chromium: 151.0.7922.34
```

נבדקו חזותית ארבע דוגמאות מן ה־raster האמיתי: members/rejection ו־admin
matches ב־360, settings ו־home ב־1440. לא נצפו חיתוך, חפיפה או גלילה אופקית
של הדף. ניווט הליגה הוא scroller רכיבי מכוון; כל target בו מובא במלואו
ל־viewport בעת Tab ונבדק כך, ולכן אינו page overflow או target אבוד.

ההבדל המדויק נשמר גלוי: לפי מקור Chromium, הדגל
[`force-device-scale-factor`](https://chromium.googlesource.com/chromium/src/+/06b3960db2aaba85d53b6e258001fabebb7d35fd/ui/display/display_switches.cc)
מחליף את device scale של **ממשק הדפדפן והתוכן**. לעומת זאת browser/page zoom
הוא מכפיל נפרד; קוד Blink מציין ששינוי browser zoom אמור לגרום ל־page reflow,
בעוד device scale משמש בנפרד לחישוב viewport
([מקור Chromium](https://chromium.googlesource.com/chromium/src/+/c0c69be50d661fd4952865e0aaf76952d9272f17/third_party/blink/renderer/core/exported/web_view_impl.h)).
לכן forced DSF הוא browser-process scaling אמיתי ועדיף מה־DPR emulation
ההיסטורי, אך הוא אינו הוכחה שה־HostZoomMap של Chrome הוגדר ל־200%. חמשת
רוחבי ה־CSS מכסים את תוצאת ה־reflow שהaudit צריך; ה־spot-check למטה נשאר רק
למסלול page-zoom ולפערי rounding אפשריים.

## תוצאת spot-check של Chrome Zoom

`OWNER_REPORTED PASS` על candidate SHA
`4b77e2412336ed1151849c5db8d05d5947a46e45`:

1. בעל הפרויקט אישר שימוש ב־Chrome רגיל עם **Menu → Zoom → 200%** לאורך
   הבדיקה, ללא CSS zoom, ‏Device Toolbar או emulation.
2. בוצע מעבר keyboard-only על `/admin/matches`, על
   `/leagues/<owned-league>/members` כולל invalid rejection, ועל
   `/leagues/<owned-league>/settings`. ה־focus היה גלוי, ולא נצפו control או

3. שילוב הדפדפן של ה־agent לא היה זמין, ולכן התוצאה מבוססת במפורש על דיווח

ה־spot-check נדרש מפני שרק פקד Zoom מפעיל את מנגנון page zoom/HostZoomMap.
אישור הבעלים סוגר את הפער הזה, ולכן S9-DEF-022 מסומן `VERIFIED`.
