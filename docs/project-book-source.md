## 1. תקציר מנהלים

המערכת מחליפה תהליך ידני: מנהל/ת יוצר/ת ליגה, משתף/ת הזמנה פרטית, מקבל/ת בקשות הצטרפות והוכחות תמונה מסוג Demo, מאשר/ת חברים, מפעיל/ה את הליגה ומסיים/ת אותה לאחר שכל המשחקים הגיעו למצב סופי. חברי הליגה שומרים ניחושים לפני נעילה ורואים דירוג נוכחי או סופי בהתאם למחזור החיים.

| ממד | ערך נמדד |
| --- | --- |
| מחסנית | Next.js 16 App Router, TypeScript strict, Supabase, Vercel |
| ממשק | 18 עמודים, 9 משטחי loading, מצבי error ו־not-found |
| מוטציות | 17 Server Actions ו־5 Route Handlers |

| תלויות ייצור | תשע חבילות בלבד |

### חמש ההחלטות שמגדירות את המוצר

1. נעילת ניחושים נקבעת לפי זמן מסד הנתונים ולא לפי שעון הדפדפן. הספירה לאחור במסך היא עזר חוויה בלבד.
2. הניקוד נכתב מחדש בכל פעם ולעולם אינו מצטבר, ולכן ריצה כפולה או תיקון תוצאה אינם מכפילים נקודות.
3. כל טבלה חשופה נוצרת באותה migration יחד עם RLS והרשאות מזעריות; השרת בודק הרשאה כדי להחזיר שגיאה טובה, והמסד בודק אותה שוב כדי שלא ניתן יהיה לעקוף אותו.
4. הוכחות ההדגמה נשמרות ב־bucket פרטי, מקודדות מחדש בשרת ונגישות רק בקישור חתום קצר לאחר בדיקת הרשאה על המשאב עצמו.
5. ספק הספורט החיצוני אינו תנאי לפעולת המוצר; המסלול הידני והקטלוג המקומי עובדים תמיד.

ליגת ניחושים עם דמי השתתפות ופרסים כספיים היא בדיוק סוג המוצר שדורש בדיקה משפטית לפני השקה. בדין הישראלי קיימים איסורים על ארגון משחקים אסורים, הגרלות והימורים, והעובדה שהכסף עובר מחוץ לפלטפורמה אינה מספיקה כדי להכשיר את המודל.

## 3. אפיון מוצר

### הבעיה שהמוצר פותר

- ניחושים נאספים בפורמט לא אחיד ובערוצים שקשה לעקוב אחריהם.
- מנהל הליגה מחשב ידנית נקודות, דירוג, שוויונות ופרסים.
- קשה להוכיח אם ניחוש הוזן לפני מועד הנעילה.
- אין תמונת מצב מסודרת של בקשות הצטרפות והוכחות.
- מחלוקות נוצרות סביב שינויי מועדים, תיקוני תוצאה וחלוקת מקום בשוויון.

### משתמשים, לקוח ותפקידים

| תפקיד | צורך מרכזי |
| --- | --- |
| אורח | להבין את המוצר ולהירשם |
| מבקש הצטרפות | לראות פרטי ליגה, להעלות הוכחה ולעקוב אחר סטטוס |

### מטרות עסקיות

1. להפחית את זמן הניהול הידני של ליגת ניחושים.
2. לצמצם טעויות ומחלוקות באמצעות חוקים ומועדים שקופים.
3. להגדיל את שיעור המשתתפים שמגישים ניחוש בזמן.
4. לאפשר למנהל להפעיל ליגה נוספת בלי להגדיל את עומס העבודה.
5. ליצור בסיס למוצר SaaS עתידי בלי להעמיס מודל מנויים על ה־MVP.

## 4. ארכיטקטורת התוכנה

המערכת היא מונוליט מודולרי יחיד של Next.js 16 ו־TypeScript strict, נפרס ב־Vercel ומשתמש ב־Supabase PostgreSQL, Auth, Storage ו־Cron. Server Components מבצעים קריאות, Server Actions מטפלים במוטציות UI, Route Handlers מקבלים upload, Cron ו־HTTP חיצוני, ושירותי feature משותפים מחזיקים את החוקים העסקיים.

Backend נפרד נדחה במודע: הוא היה מוסיף גבול רשת, CORS, העברת session, שירות פריסה נוסף וכפל בדיקות, בלי צורך מוצרי שמצדיק זאת. אם הסנכרון יחרוג ממגבלות הפלטפורמה, מוציאים רק אותו ל־worker ולא מפצלים את המוצר מראש.

### זרימת המידע

הדפדפן פונה ל־Next.js בלבד, עם session ב־cookies מאובטחים. השרת קורא ומעדכן את Supabase עם זהות המשתמש ומפתח ציבורי תחת RLS, ורק מסלולי מערכת מצומצמים משתמשים במפתח השרת. ספק הספורט נקרא מהשרת בלבד; הנתונים נשמרים במסד לפני שהמוצר מציג אותם, ולכן כל עמוד משתמש קורא מ־PostgreSQL. Supabase Cron פונה בחזרה אל נתיב הסנכרון עם סוד ייעודי.

### המחסנית והנימוק לכל בחירה

| שכבה | בחירה | נימוק |
| --- | --- | --- |
| Web | Next.js 16 App Router | דרישת קורס; Server Components, Actions ו־Route Handlers באותה פריסה |
| שפה | TypeScript strict | חוזים משותפים ובדיקות בזמן קומפילציה |
| UI | React ו־Tailwind CSS | מתאים ל־RTL ול־responsive בלי מערכת UI כבדה |
| Validation | Zod | schema אחד לכל גבול קלט בשרת; אינו מחליף אילוצי מסד |
| Database | Supabase PostgreSQL | דרישת קורס; transactions, constraints, RLS ופונקציות |
| Authentication | Supabase Auth ו־`@supabase/ssr` | session מבוסס cookies ושילוב טבעי עם RLS |
| Files | Supabase Storage, bucket פרטי | הפרדה מה־webroot וקישורים חתומים קצרים |
| הקשחת תמונה | `file-type` ו־`sharp` | ל־Node אין זיהוי magic bytes או codec תמונה בטוח מובנים |
| Scheduling | Supabase Cron ו־Route Handler | תדירות הסנכרון גבוהה ממה שתכנית ה־Cron של הפלטפורמה מספקת |
| בדיקות | Vitest, pgTAP, Playwright | חוקים טהורים, אכיפת מסד, וזרימות משתמש בדפדפן אמיתי |
| Hosting | Vercel | דרישת קורס ואינטגרציה טבעית עם Next.js |

> לא נוספו Redux, ORM, queue, microservice או cache חיצוני. הוספת שכבה כזו בלי מדידה שמצדיקה אותה היא עלות ולא ערך.

| נתיב | תפקיד |
| --- | --- |
| `GET /auth/confirm` | החלפת PKCE code ב־session והפניה בטוחה ליעד פנימי |
| `POST /api/invites/[publicId]/exchange` | המרת digest של secret ההזמנה ל־cookie קצר־חיים ומוגבל־נתיב |
| `POST /api/join-requests/[requestId]/proofs` | אימות, פענוח וקידוד מחדש של הוכחה ל־WebP פרטי |
| `GET /api/payment-proofs/[proofId]` | בדיקת הרשאה והפניה לקישור חתום של עד 60 שניות |
| `POST /api/cron/sync` | סנכרון עם claim, apply ו־finalize מגודרים |

כל Server Action נחשב endpoint ציבורי מבחינת מודל האיום: הוא טוען session מהשרת, מאמת קלט עם Zod, בודק הרשאה מול המשאב בפועל ולא מול תפקיד כללי, קורא ל־Service או לפונקציית מסד, מחזיר תוצאה טיפוסית, ורק אחרי commit מוצלח מרענן cache.

### הלוגיקה העסקית המרכזית

- **נעילה.** `save_prediction` מאמתת חברות פעילה, התאמת עונה, היעדר latch וזמן מסד מוקדם מ־kickoff, באותה פעולת כתיבה.
- **ניקוד.** `score_match` נועלת את המשחק, מעלה `result_version` כשהתוצאה השתנתה, ומעדכנת set-based את כל הניחושים. היא כותבת `points` מחדש ולעולם אינה מוסיפה, ולכן ריצה כפולה או תיקון אינם מכפילים ניקוד.
- **דירוג.** ה־view מתחיל מכל החברים הפעילים עם `LEFT JOIN` לניחושים, כך שגם חבר בלי ניחושים מופיע עם 0, ומדרג עם `rank()` ולא `dense_rank()`: שני חברים במקום 1 תופסים 1–2 והבא אחריהם 3.
- **מחזור חיים.** `start_league` ו־`complete_league` הן פעולות אטומיות ואידמפוטנטיות; `activate_due_leagues` היא ה־fallback שמקבע את הסטטוס לא יאוחר מ־kickoff הראשון. ההשלמה מקפיאה snapshot של המשחקים וסוגרת בקשות פתוחות באותה טרנזקציה.
- **תיקון מאוחר.** `resolve_match_result_review` ו־`reconcile_completed_league` הן הדרך היחידה לשנות ליגה שהושלמה, והן מפורשות, מורשות ומתועדות.
- **סנכרון.** claim, apply ו־finalize מאומתים מול generation, token ותוקף בתחילת הפעולה ובסופה, כך ש־worker ישן שהתעורר אחרי reclaim אינו יכול לכתוב.

### State, שגיאות וולידציות

PostgreSQL הוא מקור האמת העסקי היחיד. Server Components טוענים state מתמשך, Client Components מחזיקים רק טופס, dialog, countdown ומצב pending, ופרמטרים ניתנים לשיתוף נשמרים ב־URL. אין global store ואין Context לנתוני שרת.

| Code | הודעה למשתמש |
| --- | --- |
| `UNAUTHENTICATED` ו־`FORBIDDEN` | יש להתחבר; אין הרשאה לפעולה |
| `VALIDATION_ERROR` | תיקון השדות המסומנים |
| `PREDICTION_LOCKED` ו־`MATCH_NOT_STARTED` | המשחק ננעל; אפשר להזין תוצאה רק אחרי מועד הפתיחה |
| `STATE_CONFLICT` ו־`RATE_LIMITED` | המידע השתנה ויש לרענן; יש לנסות מאוחר יותר |
| `UPLOAD_REJECTED` | סוג או גודל קובץ לא תקין |
| `PROVIDER_UNAVAILABLE` ו־`INTERNAL_ERROR` | מוצגים הנתונים האחרונים; אירעה שגיאה, ללא פרטים טכניים |

Zod נותן שגיאות מוקדמות, ו־PostgreSQL אוכף את אותם כללים שוב: שם תצוגה 2–50 אחרי trim, שם ליגה 3–80, תוצאות 0–30, נקודות ניקוד 0–100 בסדר יורד, מיקומי פרס רצופים, אחוזים שמסתכמים בדיוק ב־10000 נקודות בסיס, סיבת דחייה 3–300, ותמונה אחת עד 4MB עם סוג, חתימה ופענוח תקינים. לוגים מסננים Email, tokens, סודות, קישורים חתומים ונתיבי הוכחות.

### חוויית משתמש

הממשק כולו `dir="rtl"` ו־mobile-first; טבלאות גדולות הופכות לכרטיסים או לגלילה נגישה. הספירה לאחור מציגה גם שעה מוחלטת ואזור זמן, ניחוש שנשמר מציג חותמת זמן מהשרת, וכפתור מוטציה מושבת בזמן pending אף שהמסד עדיין אידמפוטנטי. השפה החזותית היא לוח שליטה ספורטיבי בהיר, ונמנעת במכוון משפה חזותית של קזינו או הימורים.

- **ממשק.** עברית ו־RTL, סדר בית־חוץ, labels ושיוך הודעות שגיאה, focus, יעדי מגע, מצבי loading, ריק, שגיאה והצלחה, והיעדר גלילה אופקית.

## 9. סקייל בסיסי

יעד ה־MVP הוא עשרות עד מאות משתמשים, מספר קטן של ליגות פעילות ועונה אחת. בטווח הזה הארכיטקטורה עומדת בעומס בלי תוספת תשתית: PostgreSQL הוא מקור האמת, Server Components קוראים נתונים מסוננים, והניקוד מתבצע set-based במסד ולא בלולאה.

- **שאילתות כבדות.** טבלת הדירוג היא הכבדה ביותר, ואחריה רשימת המשחקים, ספירות הדוח ומתכנן הסנכרון. תוכניות ההרצה נמדדות בשער ייעודי ולא מוערכות.
- **אינדקסים.** נגזרים מדפוסי גישה אמיתיים בלבד; כל פריט של יועץ הביצועים קיבל החלטה מפורשת של הוספה, אי־הוספה או ויתור, ואין מחיקה או הוספה עיוורת.
- **מניעת טעינה מיותרת.** בוחרים רק עמודות נדרשות ומסננים במפורש; ספירות הדוח אינן מעבירות שורות; אין קריאת ספק במסלול בקשה של משתמש.
- **Pagination.** המחזור הוא ה־pagination הטבעי של מסך המשחקים, ורשימות המנהל וה־Dashboard משתמשות ב־keyset pagination במקום תקרה שקוטעת בשקט. תקרה שנחצית נכשלת סגור במקום להציג רשימה חלקית.
- **הפרדת לקוח ושרת.** כל קריאה, הרשאה, נעילה, ניקוד וגישה לקובץ מתרחשות בשרת או במסד; כפתור מוסתר אינו נחשב הגנה.
- **מכסת הספק.** בדיקת due כל דקה שאינה צורכת קריאה כשאין עבודה, רענון ממוקד של קבוצת מזהים חסומה, reconciliation ו־catalog במרווחי שעות; מרווח גדול נשמר מתחת לתקרה היומית.

### מגבלות ידועות ושיפורים עתידיים

| מגבלה | מתי השיפור מוצדק |
| --- | --- |
| דירוג בשאילתה רגילה אינו מיועד לאלפי משתתפים בליגה | materialized leaderboard, רק כשמדידה תראה חריגה |
| מכסת קצב נשמרת ב־PostgreSQL | מנגנון ייעודי, כשהתעבורה מצדיקה או במעבר לריבוי אזורים |
| הסנכרון רץ במחזור חיים של בקשה ומוגבל ב־lease | worker נפרד או renew, אם ריצה תקינה מתקרבת לתוקף |
| כתובת יוצאת משותפת עלולה לגרום 429 שאינו שלנו | static egress, אם זו תהפוך לבעיה נמדדת |
| היסטוריית סנכרון ללא retention | מדיניות שמירה, אחרי מדידת גודל בפועל |

> העיקרון החוזר: כל שיפור סקייל מותנה במדידה. הוספת cache, queue או view משוכפל "ליתר ביטחון" מוסיפה מורכבות ונקודות כשל בלי ערך מוכח בקנה המידה הנוכחי.

## 10. אבטחה בסיסית

כל קלט דפדפן, URL, טופס, קובץ וספק נחשב לא־מהימן ונבדק בשרת. אותה אמת נאכפת שוב באילוצי PostgreSQL וב־RLS; שכבה אחת לבדה אינה נחשבת הגנה.

### גבולות אבטחה

- זהות המשתמש נגזרת מ־session מאומת; הרשאה נבדקת מול המשאב ו־RLS מוסיף הגנה במסד.
- כל טבלה חשופה נוצרת יחד עם RLS והרשאות מזעריות; זמן מסד הנתונים הוא הקובע לנעילה.
- הוכחות נשמרות ב־bucket פרטי, עוברות בדיקת חתימה וקידוד מחדש ל־WebP, ונגישות בקישור חתום קצר רק לאחר הרשאת משאב.
- מפתחות שרת אינם מגיעים ל־Client bundle; מפתח הספורט מיועד ל־Production בלבד והמסלול הידני נשאר ברירת המחדל ל־Local, Preview ו־CI.
- טקסט תצוגה דוחה תווי כיווניות בלתי־נראים ומוצג בבידוד כיוון מתאים.

### אימות והרשאה

ההזדהות היא Email וסיסמה באמצעות Supabase Auth, עם session ב־cookies של SSR; אין token ידני ב־`localStorage` ואין state גלובלי. ה־proxy מרענן session בלבד, וכל עמוד ופעולה מוגנים קוראים את המשתמש מחדש. קישורי Email משתמשים ב־PKCE, ונתיב האישור מוחק את פרטי ה־token, חוסם יעדים שאינם ברשימה מותרת ומוסיף מדיניות referrer מחמירה.

ההרשאה נבדקת בשלוש שכבות בלתי תלויות: השרת גוזר את הזהות מן ה־session ולעולם לא מקלט הלקוח; כל פעולה בודקת הרשאה מול המשאב בפועל; ו־RLS בודקת אותה שוב, כך שגם עקיפה של שכבת האפליקציה אינה מחזירה שורה אסורה.

### הגנה על קריאות והעלאות

ההעלאה היא Route Handler ולא Server Action, כדי לשלוט במפורש בגבולות הגודל ולבדוק Origin לפני קריאת הקובץ. היא מקבלת JPEG, PNG או WebP בלבד, בודקת סיומת, MIME מוצהר ו־magic bytes בנפרד, מפענחת ומקודדת מחדש בהגבלת פיקסלים, שומרת רק את הפלט, מייצרת שם קובץ בשרת ומגבילה מכסה וקצב. ה־bucket פרטי וללא policies ללקוח, ולכן גישה ישירה נדחית תמיד. נתיב הסנכרון מאמת סוד ייעודי בהשוואה בזמן קבוע ובודק את ה־actor שוב בתוך פונקציית המסד; בקשה לא מורשית אינה כותבת שורת ריצה ואינה כותבת audit.

### סודות

| סוד | כלל |
| --- | --- |
| מפתח השרת של Supabase | עוקף RLS; מוגדר במודול יחיד עם `server-only` ונצרך רק בשערים מצומצמים |
| סוד ה־Cron | נשמר בסביבת הפריסה וב־Vault, לא ב־migration ולא ב־Git |
| מזהה ה־actor של הסנכרון | principal לא־אינטראקטיבי; אינו credential להתחברות |
| מפתח ספק הספורט | Production בלבד; לעולם לא לדפדפן, לא למסד ולא ללוג |
| המפתח הציבורי | מותר בדפדפן, ובטוח רק משום ש־RLS תקינה על כל טבלה |

בדיקת boundary נכשלת אם לקוח השרת מיובא מחוץ לשערים המורשים, וכל build נסרק כדי לוודא שאף סוד שרת אינו מופיע ב־artifacts של הלקוח.

### סיכונים שעדיין קיימים

| סיכון שיורי | בקרה מפצה |
| --- | --- |
| הגנת סיסמאות שדלפו אינה זמינה בתכנית הנוכחית | מדיניות אורך, מכסות קצב, שחזור שאינו חושף קיום חשבון והיקף Demo |
| אין סריקת malware | זיהוי חתימה הוא best-effort; allowlist, קידוד מחדש חד־כיווני ו־bucket פרטי |
| אמינות Email בסביבה המארחת | שער owner מתועד; המסלול המקומי מכוסה בבדיקות |
| אין אכיפת הגנת branch בתכנית הנוכחית | שחרור מבוקר ידנית ורשימת שערים מפורשת |

## 11. פריסה, הרצה מקומית ומשתני סביבה

| מה | כתובת |
| --- | --- |
| האפליקציה | [פריסת Production](https://predictor-swart.vercel.app) |
| הקוד | [מאגר הקוד](https://github.com/talzantkeren/predictor) |
| חוזה הפריסה וה־callbacks | [פריסה ו־callbacks](deployment.md) |
| מסלול הבוחן | [הוראות evaluator](evaluator-runbook.md) |

Preview משמש smoke ציבורי בלבד; אימות ב־Preview מסווג כלא נתמך ולא מאומת, ואין לו כתובת יציבה. קישורי Preview ישנים הם ראיה היסטורית ולא endpoints נתמכים.

### הרצה מקומית

1. מתקינים Node.js 24, Docker Desktop ותלויות באמצעות `npm ci`.
2. מעתיקים `.env.example` ל־`.env.local`, מפעילים Supabase מקומי ומעתיקים אליו את כתובת ה־API, המפתח הציבורי ומפתח השרת מתוך פלט הסטטוס.
3. מריצים `npm run dev` ופותחים את האפליקציה המקומית; אישורי Email נקראים דרך Mailpit המקומי.
4. לפני מסירה מריצים `npm run verify` ו־`npm run build`.

ה־Supabase CLI מותקן כתלות פיתוח ולכן אין צורך בהתקנה גלובלית. אין להדפיס או לשמור ב־Git ערכים של מפתח השרת, JWTs או סיסמת המסד, ו־`supabase db reset` מותר רק מול המסד המקומי.

### משתני סביבה

| משתנה | צד | שימוש |
| --- | --- | --- |
| `NEXT_PUBLIC_APP_URL` | לקוח | כתובת האפליקציה; משמשת גם לבדיקת Origin |
| `NEXT_PUBLIC_SUPABASE_URL` ו־`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | לקוח | כתובת הפרויקט ומפתח ציבורי המותר בדפדפן עם RLS |
| `SUPABASE_SECRET_KEY` | שרת | שערים מצומצמים של אחסון, ניקוד וסנכרון בלבד |
| `CRON_SECRET` ו־`SYNC_SYSTEM_ACTOR_ID` | שרת | סוד Bearer ו־principal לא־אינטראקטיבי לנתיב הסנכרון |
| `SPORTS_API_PROVIDER` ו־`SPORTS_API_KEY` | שרת | ידני או API-Football; המפתח מוגדר ב־Production בלבד |
| `DEMO_MODE` | שרת | חייב להיות דלוק בפריסת הקורס |

אימות משתני הסביבה מתבצע עם Zod בצד שרת: ספק שלא הוגדר מקבל את המסלול הידני, וספק חי בלי מפתח נכשל סגור לפני כל קריאת רשת. כתובת הבסיס של הספק קבועה במודול server-only ואינה משתנה סביבה, כדי לא ליצור משטח SSRF.

## 12. שימוש בסוכני קידוד ואחריות על הקוד

מסמך הקורס מתיר ואף ממליץ להשתמש בסוכני קידוד, ומדגיש שהאחריות על הקוד היא של המגיש. סוכנים שימשו לתכנון, לכתיבת קומפוננטות ובדיקות, לשיפור ממשק, לאיתור באגים ולתיעוד — תמיד בגבולות מסמכים קנוניים ולא כתחליף להם.

בשורש המאגר יושב קובץ כללי עבודה מחייב לכל סוכן. הוא אינו מסמך מוצר נוסף אלא שכבת ממשל, והכללים המרכזיים שבו הם: לקרוא את המקורות הקנוניים לפי סדר לפני כל שינוי; לא להסכים אוטומטית למימוש מבוקש אלא לבחון אותו מול חוקי המוצר, האבטחה והדדליין; לעדכן מסמך וקוד באותו שינוי; לעצור ולפתור במפורש כשקוד ומסמך סותרים; ולא לטעון ששער בדיקה עבר אם הוא לא רץ בפועל.

המנגנון הזה הוא שהפיק את המשמעת שנראית לאורך המסמך: תשע תלויות ייצור בלבד, היעדר ORM ו־state library, והצגת ממצאים פתוחים במקום סגירתם בשקט. לפני המימוש בוצעה ביקורת שער שחרור עצמאית שקראה קוד, migrations, RLS, בדיקות, CI והגדרות מול המסמכים, והפיקה פנקס מסירה מדורג שכל רשומה בו נסגרת רק עם ראיה חדשה.

## 13. הכנה להצגת המוצר

חבילת ההצגה נשמרת במלואה ב־[חבילת המצגת](../presentation/README.md): מצגת בת שלושה־עשר שקפים עם speaker notes, תסריט הדגמה של 10–15 דקות, מדריך תזמון, checklist לבוחן וצילומי גיבוי. המצגת נוצרת מקוד ואינה נערכת ביד.

| נושא בהצגה | המסר שצריך להישאר |
| --- | --- |
| הבעיה והמוצר | כשליגה מתנהלת בצ׳אט אין מקור אמת אחד |
| תפקידים והרשאות | ההרשאה תחומה לליגה, ונאכפת בשרת ובמסד |
| הדגמה חיה | המחזור המלא נראה בדמו, בלי קיצור דרך |
| ארכיטקטורה ונתונים | יישום אחד; כל כלל נאכף בשכבה הנכונה |
| אבטחה ונעילה | הגנה בשכבות; את מועד הנעילה קובע המסד |
| השלמת ליגה | סיום הוא הקפאה אטומית ולא עדכון רגיל |
| בדיקות וסקייל | כל שכבת בדיקה מוכיחה אמת אחרת; קנה מידה נמדד ולא מובטח |
| גבולות ועתיד | גבולות אמיתיים עדיפים על הבטחות |

ההדגמה מתבצעת מול האפליקציה המקומית ו־Supabase מקומי חד־פעמי; Production נפתח בסיום ככתובת ציבורית בלבד, בלי התחברות או שינוי נתונים. אם הרשת נופלת, עוברים לצילומי הגיבוי שהוכנו מראש.

## 14. קריטריוני הצלחה

- הזרימה Draft → Open → Active/current → Completed/final ניתנת להדגמה דרך המוצר.
- ניחוש אינו נשמר אחרי נעילה ואינו נחשף לאחרים לפני kickoff.
- ניקוד חוזר ותיקון תוצאה נשארים דטרמיניסטיים; דירוג סופי מוקפא ומיושב במפורש.
- משתמש אינו קורא או משנה משאב של משתמש או ליגה אחרים.
- הוכחות תמונה אינן ציבוריות, אינן נשמרות גולמיות ואינן מוצגות כמסמך כספי.
- Manual fallback עובד גם כאשר ספק הספורט אינו זמין.
- תיעוד, קוד, בדיקות וגרסת ההדגמה מתייחסים לאותו candidate SHA.

## 15. מצב הפרויקט ושערים פתוחים

Slice 9 היא הפרוסה הנוכחית: מחזור החיים, ההקשחה וחבילת ההצגה מומשו. שערי מסירה אנושיים ו־Hosted שאינם ניתנים לאוטומציה נשארים מפורשים ואינם מוצגים כ־PASS.

| שער שנותר | מה נדרש |
| --- | --- |
| אמינות אישור ושחזור בסביבה המארחת | אישור owner על מסלול המסירה בפועל |
| תזמון הסנכרון בסביבת Production | סגירה מול ה־SHA הסופי שנפרס |
| זום דפדפן native ב־200% | spot-check ידני קצר במסכים שנבחרו |
| חזרה על ההצגה | חזרה אנושית רציפה של 10–15 דקות והשלמת ה־checklist |
| גישת evaluator | מסירת זהות מאושרת ושיטת גישה מאושרת להדגמה |

> פנקס המסירה מפריד בין רשומות שנסגרו בראיה חדשה לבין שערים שנשארים בידי owner. רשומה נסגרת רק לאחר עמידה מלאה בתנאי הקבלה שלה וצירוף regression שהיה נכשל ללא התיקון.

## 16. מה לא מפתחים לפני ההגשה

- כסף אמיתי, סליקה, העברה, מסמך כספי אמיתי או תפעול פרס כספי.
- אינטגרציות מודל מחולל או יכולת שאינה נדרשת לזרימות הקורס.
- אפליקציה ייעודית לטלפון, צ׳אט, פיד חברתי, avatars או gamification נוסף.
- microservice, ORM, queue, cache חיצוני או ספריית state גלובלית ללא שינוי ארכיטקטורה מאושר.
