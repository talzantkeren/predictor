# תסריט הדגמה — Predictor1

מטרת התסריט היא הדגמה רציפה של 10–15 דקות. המחזור החי מתבצע רק מול האפליקציה
המקומית ו־Supabase מקומי disposable, דרך ממשק המוצר. אין לבצע mutation ישיר
במסד כדי ליצור מצב שנראה למשתמש. Production הוא קישור ציבורי נפרד שמוצג רק
בסיום; אין להתחבר אליו ואין לשנות בו נתונים בזמן ההדגמה.

אין לחשוף סיסמה, token, קטע סודי של הזמנה, כתובת דוא״ל, signed URL, נתיב proof
או payload של ספק. מצב Demo אינו תשלום, קבלה או פעולה פיננסית אמיתית.

## בחירת המצגת למסירה

המצגת בת 13 השקפים שבמאגר היא ראיית reproducibility פנימית. החזרה הרשמית
מתבצעת על `Predictor1_Final_Presentation_HE.pptx`, המצגת החיצונית בת 18
השקפים שבחר ה־owner ושמורה byte-for-byte. משתמשים במסלול **12:25** שב־
`timing-guide.md`: נושאי התסריט שלהלן נשמרים, אך שקף הבעיה הוא 3, התפקידים
הם 4, והארכיטקטורה עד הסקייל הם 5–11. שקף 12 מסכם את היכולות כמחזור אחד,
שקף 13 מאחד גבולות ועתיד, ושקפים 14–18 הם צילומי מסך עם talk track לפי מה
שנראה בלבד. אין להשתמש ב־notes החוזרים של 14–18. לאחר שקף 18 פותחים ידנית
את Production ואת GitHub, משום שבקובץ הנבחר הכתובות הן טקסט רגיל.

## הכנה לפני תחילת המדידה

1. לעבור לענף המועמד, למשוך אותו ולרשום ביומן החזרה את הפלט של
   `git rev-parse HEAD`.
2. להריץ `npm.cmd run presentation:build:check` רק על ראיית המאגר, ולוודא
   ש־13/13 השקפים והרינדורים הפנימיים תואמים. בנפרד לפתוח את המצגת הנבחרת,
   לאמת את ה־SHA המתועד ואת 18/18 השקפים, ולא להפעיל עליה generator.
3. להפעיל Supabase מקומי disposable ואת היישום המקומי ב־Production build,
   כאשר `SPORTS_API_PROVIDER=manual` וללא credential של ספק Sports.
4. להכין שתי sessions מקומיות נפרדות: מנהל ליגה וחבר. פרטי החשבונות נשארים
   מחוץ ל־Git ואינם מוקלדים בזמן שיתוף מסך.
5. לפתוח מראש, בלי להציג, את חמש תמונות הגיבוי לפי הסדר:

   - `fallback/01-open-league.png` — ליגה פתוחה.
   - `fallback/02-open-approved-members.png` — החבר אושר ומופיע ברשימה הפרטית.
   - `fallback/03-active-current-report.png` — ליגה פעילה ודירוג נוכחי עם 3 נקודות.
   - `fallback/04-completed-final-frozen.png` — ליגה שהושלמה ודירוג סופי קפוא עם 3 נקודות.
   - `fallback/05-completed-final-reconciled.png` — reconciliation שהוחל ודירוג סופי עם 0 נקודות.

6. לפתוח את `timing-guide.md` ואת `evaluator-checklist.md`. רצף הנתונים הקבוע
   הוא ניחוש 2:1, תוצאה סופית ראשונה 2:1 ותיקון מאוחר ל־1:1.
7. להכין את כתובת Production ואת כתובת המאגר בלשוניות נפרדות, אך להשאיר אותן
   סגורות עד נקודת הסיום במסלול שנבחר. Production אינו סביבת ההדגמה החיה.
8. להפעיל את הטיימר רק לאחר שכל הסביבה המקומית, המצגת ותמונות הגיבוי מוכנות.

## מהלך מתוזמן

### 00:00–00:25 — שקף 1: התזה

לומר: “ליגה פרטית. חיזוי הוגן. דירוג סופי שנשאר סופי.” להוסיף שהמוצר הוא
Demo בלבד ושמטרת ההדגמה היא להראות כיצד אמון נשמר לאורך מחזור חיים שלם.

### 00:25–01:10 — שקף 2: הבעיה

להסביר שהניהול הידני מפזר בקשות, אסמכתאות, ניחושים ותוצאות בין כלים. השאלה
הקובעת אינה רק כמה נקודות לחשב, אלא מי הורשה, מתי הניחוש ננעל ולמה תוצאה
מאוחרת שינתה — או לא שינתה — את הדירוג.

### 01:10–01:50 — שקף 3: תפקידים

לעבור על אורח, מבקש הצטרפות, חבר פעיל, מנהל ליגה ומנהל מערכת. להדגיש שניהול
ליגה אחת אינו מעניק גישה לליגה אחרת, ושמנהל מערכת אינו נעשה חבר בליגה מעצם
התפקיד.

### 01:50–02:25 — שקף 4: מפת המחזור

להציג את הרצף `open` → `active` → `completed`. לומר שכל שלב שיוצג מתבצע דרך
ה־UI המקומי: הזמנה ואישור, ניחוש ודירוג נוכחי, ולבסוף snapshot ודירוג סופי.

### 02:25–03:05 — שקף 5: ארכיטקטורה

להציג יישום Next.js 16 יחיד: Server Components לקריאות, Server Actions
למוטציות UI ו־Route Handlers ל־upload, ‏Cron ו־HTTP. ‏PostgreSQL מחזיק אילוצים,
RLS, זמן מסד, transactions וניקוד set-based; מה שחייב לשרוד מרוץ מוכרע במסד.

### 03:05–03:45 — שקף 6: מודל הנתונים

להראות מדוע בקשה, אסמכתה וחברות נשמרות בטבלאות נפרדות, וכיצד
`match_result_reviews`, ‏`league_match_snapshots` ו־
`league_match_reconciliations` מפרידות בין חריג תוצאה, מצב סופי ותיקון מאוחר.

### 03:45–04:35 — שקף 7: אבטחה בשכבות

להסביר את ההפרדה בין אימות session, הרשאה על המשאב, RLS ו־grants. במסלול
האסמכתה להסביר אימות חתימה, פענוח, קידוד מחדש ל־WebP, ‏bucket פרטי ו־signed URL
רק אחרי הרשאה. pagination אינו מנגנון הרשאה.

### 04:35–05:15 — שקף 8: נעילה לפי זמן מסד

להסביר שה־RPC רוכש נעילות ורק אז דוגם `clock_timestamp()`. ‏`kickoff_at` נשמר
ב־UTC, וה־countdown בדפדפן הוא עזר תצוגה בלבד. בקשה שהתחילה לפני הגבול אך
המשיכה אחריו נדחית לפי זמן המסד.

### 05:15–06:45 — UI מקומי: פתיחה, בקשה ואישור

1. כמנהל, ליצור ליגה, ליצור קישור הזמנה ולחזור לדף הליגה עד שמופיע מצב פתוח.
2. כחבר, לפתוח את ההזמנה, לפתוח בקשת הצטרפות ולהעלות תמונת Demo תקינה.
3. כמנהל, לפתוח “חברים ובקשות”, לאשר את הבקשה ולהראות ברשימה הפעילה רק את
   שם התצוגה — בלי Email, מזהה Auth או נתוני proof.
4. נקודות הגיבוי הן `01-open-league.png` ולאחר האישור
   `02-open-approved-members.png`.

### 06:45–08:15 — UI מקומי: הפעלה, ניחוש ודירוג נוכחי

1. כמנהל מערכת, ליצור משחק ידני דרך מסך הניהול עם kickoff קרוב ובטוח.
2. כמנהל הליגה, לבצע “הפעלת הליגה” מוקדם ולהראות שהסטטוס פעיל.
3. כחבר, לשמור ניחוש 2:1 לפני הנעילה.
4. לאחר ה־kickoff, כמנהל מערכת, לשמור תוצאה סופית 2:1 דרך מסך הניהול.
5. לפתוח את הדוח ולהראות “דירוג נוכחי” עם 3 נקודות.
6. נקודת הגיבוי היא `03-active-current-report.png`.

### 08:15–09:50 — שקף 9 ו־UI מקומי: השלמה ו־reconciliation

1. כמנהל הליגה, לבצע “השלמת הליגה” דרך ה־UI.
2. לפתוח את הדוח ולהראות “דירוג סופי” עם 3 נקודות.
3. להסביר שבאותה transaction מוקפא snapshot ונסגרות בקשות פתוחות בשני מצבי
   ההמתנה עם `LEAGUE_COMPLETED`, בלי למחוק אסמכתאות, היסטוריה או יומן ביקורת.
4. כמנהל מערכת, להזין תיקון מאוחר ל־1:1. להראות שהתיקון יוצר reconciliation
   ואינו משנה את הדירוג הסופי בשקט.
5. להחיל במפורש את התוצאה הסופית, לחזור לדוח ולהראות שהוא נשאר “דירוג סופי”
   ומציג 0 נקודות.
6. נקודות הגיבוי הן `04-completed-final-frozen.png` ולאחר ההחלה
   `05-completed-final-reconciled.png`.

### 09:50–10:30 — שקף 10: אסטרטגיית בדיקות

להסביר מה מוכיחות Vitest, ‏pgTAP ו־Playwright. לקרוא רק את הסכומים שמופיעים
בשקף ונמדדו בפועל על ה־SHA הסופי. להדגיש ש־CI משתמש ב־recorded fixtures
וב־fake transport ואינו פונה לספק Sports חי.

### 10:30–11:15 — שקף 11: מדידת סקייל

להציג את ארבעת ה־query plans, את צומת ה־Function Scan ואת מספרי השורות שנמדדו
על ה־SHA הסופי. להסביר keyset pagination, שאילתות תחומות וניקוד set-based.
אין להבטיח סקייל שלא נמדד.

### 11:15–12:05 — שקף 12: tradeoffs, גבולות וסיכונים

להסביר מדוע מונוליט מודולרי הוא הבחירה הקטנה והאמינה כעת. לומר במפורש:
Demo בלבד; אין פעולה כספית אמיתית; אין generative AI בזמן ריצה; וב־Local,
Preview ו־CI משתמשים רק ב־Manual adapter, ‏recorded fixtures ו־fake transport.
לציין ש־SMTP, מגבלות ספק ופעולות Hosted/Production דורשים ראיות נפרדות.

### 12:05–13:10 — שקף 13: עתיד, קישורים וסגירה

להפריד בין ה־MVP לבין המשך אפשרי: worker או materialized leaderboard רק אחרי
מדידה; כסף אמיתי רק לאחר שער משפטי; generative AI רק בשינוי היקף מאושר.

רק כעת לפתוח, בלשוניות נפרדות, את קישור ה־Production הציבורי ואת קישור המאגר
שמופיעים בשקף 13. ב־Production להציג את עמוד ה־Demo הציבורי בלבד; אין להתחבר
ואין לבצע mutation. לסיים במשפט: “Predictor1 יכול להסביר מי הורשה, מתי ננעל
ואיך נשמר הדירוג הסופי.” לעצור את הטיימר ולרשום את הזמן ביומן החזרה.

## שאלות קצרות של הבוחן

- למה יישום אחד? זהו גבול הפריסה הקטן והאמין ליעד הקורס; פיצול יגיע רק אחרי
  bottleneck מדוד.
- למה RLS וגם הרשאה בשרת? בדיקת השרת מאשרת את המשאב ומחזירה שגיאה בטוחה;
  RLS היא הגנת עומק נגד שאילתה שגויה או נתיב שנשכח.
- למה זמן מסד? שעון הדפדפן אינו אמין, ובקשות מתחרות חייבות להכריע באותו מקור זמן.
- למה snapshot? דוח סופי צריך להישאר ניתן להסבר גם אם מגיע תיקון מאוחר.
- מה קורה כשהספק אינו זמין? הנתונים השמורים והמסלול הידני נשארים זמינים;
  Local, ‏Preview ו־CI אינם תלויים בספק חי.
